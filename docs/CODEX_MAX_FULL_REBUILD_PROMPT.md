## 2. 全屏沉浸式三幕——这是本次最重要的视觉验收
目标是打开页面就像进入一个精致的国风互动游戏，不是一个左右排版的普通网站：

- 不是把整幅概念图粗暴拉伸当 3D：多层远山、雾、前景花枝、建筑、灯笼、人物分层，加入合理视差和镜头深度；真正需要空间运动的铜钱使用现有 Three.js，其他元素可以 2.5D。不得假称单张图有真实 3D 视角。
- 山海入口：整屏山海世界，四只宠物分布在自然位置，题字、简洁 CTA 融入场景，宠物可点选，用户可更换；选择状态清晰但不要把 UI 做成大列表。中央云雾/道路是进入问心台的镜头焦点。
- 问心台：整屏石台与云海，三枚铜钱是真实交互主体；输入问题、六爻进度、选中宠物和投掷按钮以不遮挡视觉重点的方式嵌入场景。六次铜钱起卦依旧正确，从下往上显示六爻；镜头升空→俯视→落地与实际随机结果一致，动画可跳过；六爻完成进入观卦阁。

## 3. 灵宠运动：从机械循环改成有生命感的动画状态机
保持四只官方造型不变，但彻底优化动作观感：
- 各自独立拥有 idle、look、blink、breathe、happy、curious、scratch-head、watch-coins、react-to-result、reading、rest 等动作状态，动作由事件驱动和非固定间隔的轻微自然变化组合，不再固定每 N 秒重复相同大动作，也不要四只整齐同步。
- idle 时有细微呼吸（身体轻柔缩放/蓬松回弹）、非同步眨眼、轻微重心转移；点击后可先停顿 0.2~0.5 秒，眼睛看向触发点、歪头、抬手挠头两下，再顺畅放回；不能突然切换图片/断帧/手臂悬浮或瞬移。角色应有“预备动作→主要动作→缓冲/回弹→自然收尾”的节奏。
- 用合适的关键帧、时间线或 spring 物理曲线，分层控制身体、帽子/叶帽、手、眼睛与挂饰的随动与滞后。每次互动选择不同轻微变体；转场时带上动作状态而不是强制重置、重复播放一段 GIF。尊重角色关节/形体，宁可做少数 3 个高质量完整动作也不要 10 个僵硬动作。
- 检查旧素材的 alpha 通道、边缘锯齿、裁切、角色参考一致性。原 GIF 仅作分镜参考；如适合可导出单独正确角色帧作为素材，否则改用分层 WebP/PNG、canvas/2D 骨骼、SVG 或纯 Three.js 动作。请勿整张拼贴图裁切出混乱小图或把 GIF 当死循环占位。
- 起卦时宠物关注铜钱而非重复挠头；等待 AI 时偶尔思考，回答出现时抬头/指向卷轴；首选轻量低耗 CPU/GPU 的方案。鼠标、触摸和 `prefers-reduced-motion` 都要正确。
- 提供每只灵宠至少 3 个真实动作（闲置、点击反馈、解卦/投币响应）的录屏或连续帧验收，并说明哪些是真实分层动效、哪些仍是静态图片。

## 4. 第一次进入的最简用户资料入口
我的产品决定：第一次使用时提供一个**轻巧、不破坏沉浸感的资料层**，界面主要是：
- **出生日期**：日期选择器，避免默认公开。
- **性别**：男 / 女 / 其他或自定义 / 不愿透露；不强行进行二元划分。
- 明确提供「跳过」并说明用途，用户不必注册；我的目标是简单、友好，而不是复杂问卷。用户若愿意只填这两项即可继续。
- 只本地保存（默认 localStorage；不要把个人资料写进日志、URL、源码或公开仓库），用户随时可以编辑/清除。明确告诉用户如启用本地 AI，这些信息只在用户同意后作为背景传给本机模型；不发送到第三方云端。
- **严格区分命理方法**：本产品第一版使用三钱六爻《周易》起卦，生日和性别不参与铜钱算法，不得声称输入它们就能“算得更准”，不得暗中虚构八字、星盘、流年或必然的性格命运结论。可以在用户同意下将年龄阶段/称呼偏好用于语境理解；没有实际帮助时不硬套性别和生日。
- 首页轻量资料设置完后，用户仍需输入**这次想问的具体问题**，然后真正起卦，不要只凭生日自动生成一卦。
- 对“考试能过吗？”这类问题，在起卦前出现**不强制**的上下文建议：考试种类、考试日期、通过标准/目标分、近期模拟成绩或准备程度；对工作/感情问题提示对应背景。不要弹出十个必填项；用户不补充也能继续。缺重要事实时，AI 不能瞎编，可以给出有针对性的追问。

## 5. AI 解卦完整重构：让人看得懂、有依据，而不是泛泛回应
现在不要只把 `qwen3:4b` 换成更大模型，先修掉产品设计缺陷：
- 彻底重做 `src/lib/interpretation.ts` 和 `src/app/api/reading/route.ts` 里约 115 字的回答限制、不能使用“卦”“爻”的过滤和过短的 `num_predict` 设计。保留健壮的输入验证、防 prompt injection、来源隔离、重试/超时/安全降级，但应允许完整连贯的中文白话分析。
- 计算、经典资料、解释**三层分离**：程序计算三枚铜钱六次结果→独立、可核验的 `zhouyi.json` 经文→AI 根据明确的结构化证据做解释和联想。AI 永远不能改本卦、动爻、变卦、卦辞和爻辞。核对 64 卦和 384 爻、乾坤用辞及出处，CText 交叉校勘待完成的内容应明确记录，不能假装已校验。
- **每次首答结构（可折叠、易读）**：① 本次问的是什么（简短复述）；② 本卦是什么、核心象征是什么；③ **卦辞逐句白话解释**，让不懂古文的人也能看懂；④ **每条动爻对应原文和通俗解释**，如多爻则按规则说明侧重点；⑤ 变卦意味着何种变化主题；⑥ 对当前问题的综合解读（可以给出偏向、障碍、条件和不确定性，但不装成绝对预测）；⑦ 两三条可操作建议和一个值得补充的具体问题。
- 例如问“我考试能过吗”：必须正面回应“从卦象的传统解释看，这更像是……，但不能据此确定是否通过”，然后结合卦辞、动爻、用户提供的模拟分数/备考背景分析，而不是直接说一些适用于任何人的“先行动再观察”“做两件小事”。如果没有成绩信息，就明确说缺哪些现实依据，并可追问 1 个最有价值的信息。
- 古籍引用、现代白话与 AI 推演在 UI 上明确标注来源和性质；**不要让模型编造古籍原文、历史出处、具体成绩或概率**。没有可靠可计算的现实数据，不提供精确通过概率；不能把生日/性别当作概率算法。古典卜筮作为文化解释和自我反思，不宣传科学预测能力。
- 多轮追问必须继承**同一次**六次投掷的卦、动爻、经文、问题、可选背景、已发对话；可以针对追问进一步解释不同爻意，而不是重新起卦或把每句话都格式化成同一个套话模板。
- 交互上先即时呈现程序已确认的卦象、卦辞和静态白话，不必等 AI 才显示；本地 Qwen 推理支持尽量流式输出/分段展示、取消与重试、过程反馈（可能持续 20~60 秒）。保持本地模型可用时真实解答；本地不可用只能明确标记「演示模式 · Mock」，不能把 mock 混进正式回答。
- 先实测已有的 `qwen3:4b`：根据本机 CPU/内存与延迟调整上下文长度、输出长度和流式渲染。只有比较效果、资源允许、且我同意时，才换成更大的本地模型；不自动下载大型模型，不擅用付费云 API。
- 建立可控的输出 schema 或分段结构，避免 JSON 太长导致解析失败；可以在原有短答基础上渐进地展示白话和专题分析，兼顾质量与等待时长。不要仅为满足模板输出堆砌空洞字数。
